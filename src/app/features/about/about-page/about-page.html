À propos

Comment ça marche

J'ai créé Spade Cup FR pour organiser les tournois de guerres amicales des clans francophones sans tableur, et sans recopier des captures d'écran à la main. Voici les règles telles que le site les applique, puis, pour les curieux, comment il est construit.

Les règles, en clair

Le format

Chaque match est une guerre amicale en {{ rules.teamSize }} contre {{ rules.teamSize }}, uniquement avec des HDV {{ rules.townHallLevel }}. Les deux chefs lancent la guerre entre eux dans le jeu, comme d'habitude. Élimination directe : on perd, on sort.

S'inscrire

Tout se passe sur le Discord : un chef tape /inscription avec le tag de son clan. Le bot vérifie que le clan existe et récupère son nom et son blason. Pas de liste de joueurs à fournir : chaque clan aligne qui il veut, du moment qu'ils sont HDV {{ rules.townHallLevel }}.

Le tirage

À la clôture des inscriptions, l'arbre est tiré au sort par l'ordinateur, avec un hasard cryptographique : personne, pas même moi, ne peut le prévoir ni l'orienter.

S'il n'y a pas pile 8, 16 ou 32 clans, certains sont exempts : qualifiés d'office pour le tour suivant. Les places vides sont réparties pour que deux exempts ne se croisent jamais.

Qui gagne ?

  1. Le clan qui a le plus d'étoiles.
  2. À égalité, le meilleur pourcentage de destruction.
  3. Encore à égalité, celui qui a attaqué le moins longtemps au total.
  4. Égalité parfaite (ça n'arrive presque jamais) : les arbitres tranchent.

Les résultats

Rien à faire : toutes les 5 minutes, le bot regarde les guerres des matchs en cours, dans l'API officielle du jeu. Quand une guerre démarre, il l'annonce ; quand elle se termine, il lit le score, qualifie le vainqueur et poste l'arbre à jour sur le Discord. Rien à recopier, donc pas d'erreur de saisie.

Seules comptent les guerres entre les deux clans qui doivent se rencontrer, lancées après que leur match est devenu jouable : une guerre d'entraînement ne change rien à l'arbre.

Un joueur qui n'est pas HDV {{ rules.townHallLevel }}, une guerre qui n'est pas en {{ rules.teamSize }} contre {{ rules.teamSize }} : le résultat est enregistré, mais signalé aux arbitres. Pour que le bot puisse lire la guerre, le journal de guerre d'au moins un des deux clans doit être public, et il ne faut pas relancer une autre guerre dans les 5 minutes qui suivent : le jeu ne garde que la dernière.

Les arbitres

Ils décident de tout ce que le site ne peut pas savoir : délais, forfaits, litiges. Si le jeu ne répond pas, ils peuvent saisir le score à la main. Gardez vos captures d'écran : en cas de désaccord, ce sont elles qui comptent.

Chaque guerre lue dans le jeu enregistre aussi la ligne de chaque joueur (étoiles, destruction, temps). C'est ce qui alimente le classement des joueurs : qui a le plus joué, qui a fait le plus d'étoiles, qui enchaîne les triples.

Sous le capot

Je suis développeur, et ce site est aussi mon projet vitrine. Il est open source : tout le code est sur GitHub.

Le site

Angular 22 : composants autonomes, signals, sans zone.js, pages chargées à la demande, données lues avec httpResource. Navigable au clavier, lisible par les lecteurs d'écran, en thème clair ou sombre.

Le serveur

Un Cloudflare Worker en TypeScript et une base SQL D1. L'API publique est en lecture seule : les écritures passent uniquement par le bot Discord.

Le bot Discord

Pas de bot connecté en permanence : à chaque commande, Discord envoie une requête HTTP signée (Ed25519), et le serveur vérifie la signature avant d'agir. Toutes les 5 minutes, une tâche planifiée joue l'arbitre ; l'image de l'arbre est une capture d'écran du site, faite par un vrai navigateur dans le cloud.

Une seule logique

Les règles (arbre, départage, lecture des guerres) sont écrites une seule fois, en TypeScript pur, et partagées par le site et le serveur. Si l'un change, le compilateur prévient l'autre.

Les tests

Plus de 250 tests automatisés, relancés à chaque modification par GitHub Actions : logique du tournoi, pages du site, et serveur testé dans le vrai moteur de Cloudflare avec une base de données jetable.

Le coût

0 €. Tout tourne sur les offres gratuites de Cloudflare, et le code est conçu pour rester dans leurs limites.

Trois problèmes que j'ai dû résoudre

  1. Une API qui exige une adresse IP fixe

    L'API du jeu n'accepte que les adresses IP déclarées à l'avance, alors qu'un serveur Cloudflare en change sans arrêt. Les requêtes passent donc par un relais à IP fixe, et l'adresse de ce relais est un simple réglage : on peut en changer sans toucher au code.

  2. Corriger une finale

    Mes tests ont montré qu'une fois la finale saisie, le tournoi passait « terminé » et le bot ne le retrouvait plus : impossible de corriger une erreur d'arbitrage. Le dernier tournoi reste désormais modifiable jusqu'à la création du suivant.

  3. Une mise à jour qui effaçait des données

    En SQLite, « remplacer » une ligne veut dire la supprimer puis la recréer. Avec les suppressions en cascade, mettre à jour un match aurait effacé les statistiques de ses joueurs. J'utilise une vraie mise à jour (un upsert), et un test le vérifie.
